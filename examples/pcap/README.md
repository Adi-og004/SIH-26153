# Demo PCAP files

Three small **synthetic** captures for the dashboard's **📥 Data Input →
📡 Upload PCAP** source. They were generated by this project's own
`src/generate_demo_pcaps.py` (Scapy, seeded with `random.seed(42)`). They
contain no third-party or real-user traffic.

| File | Size | Scenario (second half of the capture) |
|---|---|---|
| `demo_c2_beacon.pcap` | 321 KB | periodic C2-style beaconing |
| `demo_portscan.pcap` | 767 KB | port scan |
| `demo_dos_flood.pcap` | 463 KB | DoS-style flood |

Each capture is about 220 s long: 11 benign windows, then 11 attack-pattern
windows (22 × 10 s windows). The canonical pipeline turns each into
**13 sequences of shape (10, 52)**.

Two larger scenarios (`demo_lateral_movement`, `demo_exfiltration`) are not
committed. To regenerate all five into `data/sample_pcap/`, run
`python src/generate_demo_pcaps.py`.

## What to expect — read before demonstrating

On these synthetic captures the frozen V4 model does **not** cross its 0.69
alert boundary. The maximum P(t+5) is 0.035 for C2 beacon, 0.125 for port scan
and 0.254 for DoS flood. That is the documented PCAP-to-training feature gap
(see `docs/FEATURE_PARITY.md` and the README's *Reliability / Limitations*),
not a malfunction. The captures show that the PCAP path runs end to end —
packets → flows → 10 s windows → 52-D state → frozen V4 rollout. They do not
show detection performance on real attacks.

`tests/test_submission_regression.py` runs `demo_portscan.pcap` and
`demo_c2_beacon.pcap` through the exact call sequence the dashboard uses,
checks them against recorded reference outputs, and checks that re-uploading
the resulting tensor as prepared `.npy` gives bit-identical probabilities.
